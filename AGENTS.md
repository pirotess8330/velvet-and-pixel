# Website documentation and release handoffs

Before starting work, read the current canonical standards and both project records:

- Standards: https://docs.google.com/document/d/1kcesqcQoBpz6qiNinL2ja0EHSLJraawR4Lwrk5TxlKI/edit
- RELEASE_ROADMAP: https://docs.google.com/document/d/1kEP8syiAECOZimD7oZcysYCVunr3v5K6szLnYIcJrg0/edit
- PROJECT_HANDOFF: https://docs.google.com/document/d/1O6TRHD-EAeB1FXB47Ytr2QVgChvULpx6ayP-0PYDK_Y/edit
- Drive documentation folder: https://drive.google.com/drive/folders/1D-n5MhAfuSoavZyKh3SEXqiaRB-RcWQU

Update the existing Drive records in place at every development milestone,
scope change and release handoff. Do not create competing copies. Verify stack
versions against manifests/lockfile, features against source, checks against
actual output, and publication against successful deployment and live URLs.
Record commit/version, artifact provenance, acceptance, limitations and next
milestone. Distinguish planned, implemented, tested, approved and published.
Use UNVERIFIED with missing evidence when access or verification is unavailable;
report the documentation gap instead of claiming the record is current.
Preserve decision and release history, stable privacy routes, and app release
statuses supported by owner/project evidence. Website deployment is not proof
of app publication. Keep portfolio summaries non-confidential and factual.

No application functionality, infrastructure or publication is authorized by
these documentation requirements alone. User task authorization still governs.
